# 限流优化提案（2026-09-20）

> 状态：**研究结论，未实施**。线上未做任何改动。所有数据来自生产 nginx access/error log
> （近 2 天全量 + 近 14 天轮转）与代码盘点，未做压测、未改配置。

## 一、当前生效的限流（三层，全部按 IP 计）

| 层 | 位置 | 维度 | 限制 | 触发时用户看到 |
|----|------|------|------|----------------|
| nginx | `attrax_page`（页面 + RSC 预取） | IP | 10r/s，burst 40 | 429（HTML 错误页） |
| nginx | `attrax_api`（轮询 / 图片资产 / 证据） | IP | 10r/s，burst 40 | 429 |
| nginx | `attrax_scan`（扫描创建） | IP | 5r/s，burst 10 | 429 |
| nginx | `limit_conn`（代理位置） | IP | 30 并发（HTTP/2 每个并发请求算一个） | 429 |
| nginx | `limit_conn`（静态资源） | IP | 200 | 429 |
| BFF | 扫描创建 | IP | **10 次 / 60s** | 429 JSON「请求过于频繁」 |
| BFF | 补充证据 / 重扫 / 管理员登录 | IP | 10 / 5 / 5 次每 60s（登录 15min） | 429 JSON |
| RAG | 写入路径（创建扫描等） | IP | 30 次 / 60s | 429 |

关键实现细节：nginx 的 `limit_req` 带 `nodelay` —— **超出的请求立即失败（429），而不是排队等待**。
BFF 的 `resolveClientId` 优先取 `x-real-ip`（即按 IP），RAG 同理。

## 二、真实流量的实测画像（近 2 天日志，351 个真实 IP）

- 单用户单秒峰值：**22 个请求**（页面加载 + RSC 预取那一瞬间）；中位数 1
- 单用户持续速率：≈ **2 请求/秒**；重度浏览（大量预取）窗口内最高 **120 请求/分钟**
- 单次页面加载的代理请求并发：**3~6**（实测 `/`、`/upload`、`/regulations`、`/pricing`）
- 扫描期间轮询：每 2~8 秒 1 次，一次扫描 60~100 秒 ≈ 15~30 次轮询
- 扫描创建频率：重度测试者 10 次 / 50 分钟；普通用户更低

对照当前限额：页面桶余量 1.8×（22/s 对 burst 40）、API 桶余量充足、扫描桶余量充足、
`limit_conn` 余量约 5×（单页 3~6 对 30）。

## 四、建议（按性价比排序，均未实施）

### P0 — 前端把瞬时限流当"可重试"，不要直接判失败

`lib/hooks/useScanPolling.ts:213` 现在只对 **5xx** 重试；429 落进 `if (!response.ok)` 分支，
直接把扫描置为 `failed`（用户看到「Scan session expired.」，但扫描其实还在跑）。
`app/result/[sessionId]/use-result-loader.ts:102` 同理。

改法：把 429 / 503 一起纳入可重试（指数退避 + 上限），UI 显示「排队中，正在重试…」而
不是失败。**这是「不能老是返回报错」最直接、风险最低的一条**，不依赖改限额。

### P1 — 便宜的请求用"延迟"而不是"拒绝"

nginx `limit_req` 去掉 `nodelay`：burst 之内的突发**照常立即通过**（实测页面加载 22/s < burst 40，
用户完全无感），只有超出 burst 的持续超速才会被排队（rate=10r/s 时每秒最多补 10 个，
极端突发下延迟几秒），排不下的才被拒。对页面 / RSC / 轮询 / 图片资产这类"便宜且必须成功"
的请求，排队远好于 429。扫描创建保留 `nodelay`（立即拒绝，成本控制）。

同时把 burst 提高：page / api `burst 40 → 80`（约 4 个标签页同时首屏），rate 保持 10r/s
（实测持续只有 2r/s）。`limit_conn` 代理位置 `30 → 60`（HTTP/2 下每个并发请求都算一个连接，
多标签页会叠加）。

### P2 — 令牌桶的 key 从"纯 IP"改成"IP + 匿名 cookie"

所有限额现在都按 IP，CGNAT / 公司出口 / 手机网络下的多个用户（以及同一人的多个标签页、
多台设备）共享同一个桶，一个人刷页面就能让别人提交失败。建议：

- nginx 对页面 / API / 扫描三个桶改用应用下发的匿名标识（例如中间件已经注入的
  request-id cookie，或新加一个长期 `attrax_uid`）作为 key，缺失时回退 `$binary_remote_addr`
- 同时保留一个更宽的**每 IP 兜底桶**（例如 `rate=60r/s burst=200`），防止脚本刷 cookie 绕过
- BFF 的 `resolveClientId` 同理（优先 cookie，IP 作兜底）

### P3 — 成本边界只保留在"扫描创建"

每次扫描要跑一轮 LLM 并占用 5 个 RAG worker 之一最多 280 秒；页面 / 轮询 / 资产不碰 LLM。
因此真正需要严管的只有创建这一处：nginx `attrax_scan`（5r/s burst 10）+ BFF（10 次/60s）
已足够，其余路径建议放宽（P1）或改为排队。

考虑给创建失败的响应加 `Retry-After` 与 JSON 体（nginx 目前返回 HTML），让前端能直接
展示「请求过于频繁，N 秒后重试」。

### 不在本次建议范围

- 不取消限流：扫描创建的成本与 5 个 worker 槽位必须有边界
- 不改成"全局令牌桶"：单用户洪峰不应吃掉全站额度
- 504 那类上游阻塞属于容量问题（单进程 Next.js + 同步重活），需要单独排查，不要用限流掩盖

## 五、实施顺序建议

1. P0（前端重试语义）——只改前端，独立部署，直接消除"轮询撞限流就显示失败"
2. P1（nodelay + burst + limit_conn）——只改 nginx 模板，`nginx -t` 后 reload，秒级回滚
3. P2（key 改造）——需要同时加 cookie 与兜底桶，改动面较大，建议单独一轮并做压测
4. P3 的 `Retry-After` / JSON 错误体可并入 P1
