## A · 项目定位

### A1 · 一句话介绍 attrax

attrax（公开名「火鹰合规 / Blaze Hawks」）是一款面向跨境电商卖家的合规风险扫描工具：用户上传一张产品图片，AI 自动识别品类与可见特征，从规则知识库里挑出该产品在该市场必须满足的法规条款，让 LLM 按锚点生成合规报告，并对每条法规引用做确定性反向字面校验（matched / fallback / unmatched 三态）。

### A2 · 解决的真实痛点

跨境电商卖家要把一件产品同时卖给欧盟、美国、英国、日本等多国，每国都有 CE / FCC / UKCA / CCC / PSE 等不同准入要求，以及 RoHS / REACH / Prop 65 等化学物质限制。痛点有三：

1. **法规分散**：欧盟 13 篇 + 美国 12 篇 + 中国 12 篇 + 英国 5 篇 + …，没有统一入口。
2. **判读门槛高**：每一篇都是几百页法律文本，普通卖家读不完也读不懂。
3. **法规在变**：欧盟电池护照 2025 年起强制、CPSC 召回每周更新、UKCA 与 CE 切换期……卖家根本追不上。

attrax 把这三件事合并成「拍一张图，等 30 秒」。

### A3 · 目标用户

- 主：年营收 50 万 ~ 2000 万美元的跨境电商品牌方（亚马逊 / Shopify / TikTok Shop / 独立站）。
- 次：合规咨询公司（用它做初筛再人工复核）、平台方（招商 / 风控批量识别卖家上架商品）。
- 不做：纯 C 端买家（不需要）、纯境内贸易（不涉及跨境合规）。

### A4 · 与已有方案的差异

| 维度 | attrax | 传统法规库（EUR-Lex / eCFR） | 通用 LLM（直接问 ChatGPT） |
|---|---|---|---|
| 输入 | 一张产品图 + 目标市场 | 关键词搜索 | 自然语言问题 |
| 输出 | 含每条引用 match_status 的结构化报告 | 原始法条全文 | 自由文本答案 |
| 引用真实性 | 确定性字面比对（matched / fallback / unmatched） | 法规原文（无误用问题） | 无验证，幻觉风险高 |
| 法规更新 | 35 个官方源每日巡检 + 自动入库 | 人工发布 | 无 |
| 跨市场统一 | 一次扫描同时看 16 个市场 | 切网站 | 拼接多轮提问 |

## B · 架构与工程

### B1 · 整体架构是什么样的？

浏览器 → Next.js 16 standalone（端口 3000，nginx 反代到 443）→ BFF `/api/scan/*` → RAG FastAPI（端口 8001，仅 loopback）。BFF 处理鉴权 / 限流 / cookie 移交，RAG 跑扫描管线（vision → generate → verify 三步线性）。完整组件图见 [01-architecture-overview.md §顶层组件](./01-architecture-overview.md)。

### B2 · 为什么用 Next.js + FastAPI 双服务？

- Next.js：BFF + 同源 SSR = 没有 CORS 暴露，HttpOnly cookie 安全移交，server actions 与 RSC 让结果页直出。
- FastAPI：Python 生态（PyYAML / pdfplumber / requests / pydantic）天然适合法规解析与数据校验；单进程 ThreadPoolExecutor 5 并发扫描跑得动中小流量。

### B3 · 为什么端口 8001 而不是 8000？

`lib/rag-client/v1-adapter.ts` 是唯一的 RAG HTTP 封装，读取 `RAG_SERVICE_URL`；docker-compose 默认 `127.0.0.1:${RAG_PORT:-8001}:8000`（容器内 8000，宿主机 8001）。这是为了和未来可能用 8000 的其它服务隔开。

### B4 · 用了什么 AI 模型？

- 主：MiniMax-M3（Anthropic SDK 兼容，端点 `https://api.minimaxi.com/anthropic/v1`）。
- 降级：DeepSeek（识图走 OpenAI 兼容 `/chat/completions`，报告生成走 Anthropic 兼容 `/v1/messages`）。
- 不依赖任何 embedding / 向量库（2026-09-11 de-RAG 改造后整体删除），改用「规则知识库 + 法规原文 + LLM 按锚点生成」三段式。

## C · 避免幻觉（最常被问的）

### C1 · LLM 最容易胡编什么？你们怎么防？

LLM 在合规场景里最危险的胡编是「**假法规条款号 / 假引文**」。我们的防线：

1. **强制锚点清单**：system prompt 里塞进 `data/kb/anchors/*.yaml` 的锚点（`doc_name / region / reason / key_points`）。LLM 必须从这些锚点里选，不允许自创法规。
3. **注入原文**：每个锚点的 `key_articles` ID → 从 `data/regulations/{region}/*.yaml` 拉出**逐字法条正文**，塞进 prompt。LLM 看到的不是它自己的记忆，而是真的官方文本。
3. **确定性反向字面匹配**：`rag_service/verify/quote_matcher.py` 对每条 citation 做 normalize（NFKC + 全角 / 半角折叠 + 空白折叠）后的字面匹配，三态结果写到 `auditMetadata.verificationMode = "kb_exact_quote"`：
   - `matched` — 引文与官方原文逐字一致 ✅
   - `fallback_article_only` — 法规与条款是对的，引文与原文不完全字面匹配（含 `unverified` 源） ⚠️
   - `unmatched` — 法规 id 或条款 id 找不到 ❌
4. **前端三态色码**：CitationChip 显示绿 / 黄 / 红 + 「已对照原文 / 仅对照摘要 / 引用错误」文案。

完整实现见 [04-backend-pipeline.md §第 3 步](./04-backend-pipeline.md) 与 [`rag_service/verify/quote_matcher.py`](rag_service/verify/quote_matcher.py)。

### C2 · 法规引用的版本怎么保证是最新？

- 35 个官方源（EUR-Lex Cellar / eCFR JSON / Federal Register / Canada Justice XML / CPSC RSS / GOV.UK 等）每日 03:00 由 watchdog 巡检，见 [`data/regulation_sources/official_sources.json`](data/regulation_sources/official_sources.json)。
- 每次扫描报告里都暴露 `auditMetadata` 字段：本次扫描用了哪份 YAML（commit SHA + last_verified），由 `article_loader.cache_generation()` 隐式保证。
- 自动入库有四类语义（UPDATE / CREATE / MARK / EVIDENCE），完整流程见 [03-regulation-update-watchdog.md](./03-regulation-update-watchdog.md)。

### C3 · 怎么知道你们的引用确实是对的？

- 评测：`scripts/eval_grounding.py` 跑 grounding 评估（`docs/annotation/grounding-eval.md` 是标注集格式）。
- 生产可观测：每次扫描的 `report_package.auditMetadata.canonicalQuoteAttachedCount` 暴露实际 attach 了多少 canonical excerpt；`agent_trace` 里有 verify 步骤的 `matched / fallback_article_only / unmatched` 计数。
- 失败模式：把 `citation.match_status == "unmatched"` 的条目标红，结果页 EvidencePanel 显式列出。

### C4 · 「按锚点生成」会不会限制 LLM 创造力？

会，而且**故意限制**。合规场景要的不是 LLM 自由发挥，而是「按已知法规给结论」。我们给 LLM 的 prompt 同时塞了「强制锚点清单 + 逐字法条正文 + JSON Schema」，LLM 只需要做两件事：识别哪些条款对当前产品适用 + 写人话。结构化、可校验、可审计。

## D · 数据与知识库

### D1 · 覆盖哪些法规？多少篇？

44 篇。按市场分：

| 市场 | 篇数 | 例子 |
|---|---:|---|
| EU | 13 | GPSR / 玩具 / RoHS / RED / EMC / LVD / 电池新规 / REACH / 化妆品 / FCM / 纺织品 / ErP |
| US | 12 | CPSIA / CPSA / Prop 65 / FCC Part 15-18 / FDA 21 CFR 174 / MoCRA / 49 CFR / ASTM F963 / UL |
| CN | 12 | CCC / CCC-IT / CSAR / SRRC / GB 6675-5296 系列 |
| UK | 5 | UKCA / 家电 / Radio / Batteries / Cosmetics |
| AU / UN | 各 1 | RCM、UN 38.3 锂电池运输 |

完整列表与人类 URL 见 [`docs/regulations/ONLINE-REGULATIONS-AND-DAILY-SOURCES-2026-09-16.md`](docs/regulations/ONLINE-REGULATIONS-AND-DAILY-SOURCES-2026-09-16.md)。

### D2 · 国标 / UL 这种版权法规怎么存？

「private_with_summary」状态：系统内置权威 KB 提炼摘要 + 官方购买 / 标准信息公开系统查阅链接，`articles[]` 字段留空。前端 CitationChip 显示「仅对照摘要」，用户点开有 `purchase_url`。完整 license 治理在 [`rag_service/retrieval/article_loader.py:VERBATIM_ALLOWED_SOURCE_KINDS`](rag_service/retrieval/article_loader.py)。

### D3 · 多语言支持情况？

- 文案：zh-CN / en-US 双语，由 [`lib/i18n.tsx:BlazeLocaleProvider`](components/blaze-hawks) 作为真值源。
- 法规正文：当前 44 篇以英文原文入库（EU/US/UK 官方语言），其它市场本国语言会作为后续扩展。
- 报告输出：中文为主，导出 `?lang=en` 时框架字段有英文回退（[`lib/report-localization.ts`](lib/report-localization.ts)）；LLM 生成的正文本身仍中文。

### D4 · 法规怎么按品类 / 特征触发？

每个 KB anchor YAML 写明 `applies_if`：

```yaml
applies_if:
  markets: [EU]              # 目标市场
  category: [battery, ...]   # 10 大品类
  features_any: [battery]    # 电池 / 无线 / 市电 / 儿童
```

`rag_service/retrieval/must_check.py:build_anchor_list` 做品类 + 特征 + 市场三段叠加：扫描请求里的 markets 与 anchor 的 markets 取交集；feature 关键词匹配（FEATURE_KEYWORDS 在 vision 识别结果里 substring 命中）；UN 类（如 UN 38.3）始终命中。

### D5 · 法规 YAML 是怎么生成的？人工写的吗？

- 初始 44 篇是人工整理（operator 自己 + 部分咨询机构协助），结构由 [`data/regulations/regulations_index.json`](data/regulations/regulations_index.json) 索引。
- watchdog 每天 03:00 自动检测改动：
  - **UPDATE**：刷新 `last_verified` / `checksum_sha256` / `raw_file`（原 YAML 备份到 `data/regulation_supplements/auto-{date}/backup/`）。
  - **CREATE**：能映射（如 EU CELEX `32012L0019` → `EU-2012-19`）但 YAML 不存在 → 自动创建最小 public 条目 + raw_file 指针 + 空 `articles[]`。
  - **MARK**：连续 7 天失败的源标 `status: stale`，Federal Register 文档 action 含 "removal / revoke / repeal" 标 `status: repealed`。永不硬删。
  - **EVIDENCE**：所有变化都把原始 RDF / HTML / XML + 统一 diff 写到 `data/regulation_supplements/auto-{date}/{source_id}/`，可审计。

## E · 多市场 / 多品类

### E1 · 一次扫描能看几个市场？

上限是 **5 个市场** + 1 个品类。市场白名单由 [`app/api/scan/route.ts:ALLOWED_MARKETS`](app/api/scan/route.ts) Set 校验（与 `lib/types.ts:MARKET_IDS`、`rag_service/config.py:ALLOWED_MARKETS` 三方对齐）；超过 5 个时 RAG 侧 `MAX_MARKETS_PER_SCAN = 5` 返回 `INVALID_MARKETS`。默认 `["EU", "US"]`。

### E2 · 怎么扩新市场？

新增市场需要 4 件事：

1. 在 `lib/types.ts:MARKET_IDS` 与 `rag_service/config.py:ALLOWED_MARKETS` 同步加 ID（双向，2026-09-13 审计 P0-5 修过漂移）。
2. 落该市场的法规 YAML 到 `data/regulations/{region}/` + KB 锚点到 `data/kb/anchors/`。
3. watchdog 注册表 `data/regulation_sources/official_sources.json` 加监控源（机器 URL + 人类 URL）。
4. 前端多语言文案表更新。

### E3 · 视觉识别怎么知道产品是哪个品类？

走 VisionAnalyzer：把用户上传图 base64 编码发给 LLM，要求返回 JSON（`category` + `core_features` + `observations[]`）。10 大品类 + 4 硬特征是枚举闭集（`lib/types.ts:PRODUCT_CATEGORIES`）；BFF 的 `ALLOWED_CATEGORIES` 额外接受复数写法（`toy` / `toys`）以兼容历史输入。

## F · 性能与可靠性

### F1 · 一次扫描要多久？

- 正常情况：45~90 秒。其中：
    - vision：5~15 秒（MiniMax 视觉，含思考链）
    - generate：20~50 秒（MiniMax 报告生成，单次大 prompt）
    - verify：< 50 毫秒（确定性字符串比对）
- 兜底超时：280 秒（`main.py:_SCAN_TIMEOUT_SECS`），超时后 BFF 返 504。

### F2 · 并发能力？

- RAG uvicorn `--workers 1` + ThreadPoolExecutor 5（`config.py:scan_worker_concurrency`）。即同时 5 个扫描并行；第 6 个排队。
- 单进程假设：pm2 fork + 未设 instances；扩到多实例要重新设计跨进程锁。

### F3 · 怎么保证服务挂了不丢任务？

- pm2 `autorestart: true` + 进程内置调度（watchdog 也是一样）。
- `ScanService.resume_pending()` 启动扫描未完成 job，job 状态落 `data/backend/jobs/`。
- 单扫描异常退出：heartbeat 标 failed，文件保留供人工 inspect 或下次 resume。

### F4 · AI 服务挂了呢？

| 场景 | 行为 |
|---|---|
| MiniMax 视觉 API 挂 | 自动改发 DeepSeek（OpenAI 兼容 `/chat/completions`） |
| DeepSeek 也挂 | 视觉降级关闭，沿用旧的 `vision_call_failed` 行为 |
| MiniMax 报告生成挂 | 自动改发 DeepSeek（Anthropic 兼容 `/v1/messages`） |
| 双供应商全挂 | `report_package.degradedFallback=true`，UI 显示「演示回退」开关 |
| RAG 8001 完全不可达 | 前端降级为 `degraded` + 红色横幅 |

关键修复坑（来自代码注释）：
1. **降级 key 配齐时 primary 只试 1 次**：`_LLM_MAX_ATTEMPTS=3` × 90s + backoff ≈ 273s ≈ 单扫描 280s 兜底；不降一次级就耗光预算根本没机会走 DeepSeek。
2. **deepseek-flash 是 reasoning 模型**：`reasoning_content` 与 `content` 共用 completion 预算，沿用 primary 3072 预算会 HTTP 200 + 空 content。所以降级通道独立预算 `DEEPSEEK_MAX_TOKENS=16384`。

### F5 · 怎么评估报告准确度？

- grounding 评测：`scripts/eval_grounding.py`，标注集格式见 [`docs/annotation/grounding-eval.md`](docs/annotation/grounding-eval.md)。
- 法规覆盖评测：`scripts/report_regulation_coverage.py`，看每个 KB 锚点的真实使用频率。
- 端到端回归：`scripts/run-production-regression.ts`，按真实产品图跑扫描，对照上一次结果。

## G · 隐私与数据安全

### G1 · 用户上传的图片存哪？

- 临时存：`data/backend/uploads/`（gitignore），扫描结束 + 报告生成后归档（或按会话 TTL 24h 自动清理）。
- 会话元数据：`data/backend/sessions/{sessionId}.json`（仅 SHA-256 hash + 状态，不含原图）。

### G2 · 用户数据会被用来训练吗？

不会。所有调用第三方 LLM（MiniMax / DeepSeek）的请求按各自 provider 的 ToS 处理；attrax 侧不收集任何用户身份信息（无登录、无 IP 长期存储），仅 nginx `access.log` 与 RAG 进程内限流 Map 用于运营。

### G3 · 是否合规？

- GDPR：用户上传图与查询不与个人身份绑定；扫描结果 24h TTL；用户主动删除会话 = `rm /opt/attrax/data/backend/sessions/{id}.json`（FileBackend 真值）。
- 数据出境：图片与文本随 LLM 调用出境（MiniMax / DeepSeek 在中国大陆），已在用户上传页告知。
- 隐私政策文档：见项目内 [`docs/privacy.md`]（如有）。

### G4 · 你们怎么保证密钥不泄露？

- 所有密钥（MiniMax / DeepSeek / RAG_INTERNAL_SECRET）只在 `/opt/attrax/.env*` / `/opt/attrax/.rag-internal-secret`，权限 `600`，归属 `ubuntu:ubuntu`。
- `.env*` 在 `.gitignore`，git 历史里暴露过的旧 secret 已轮换失效（详见 [`docs/SECURITY.md`](docs/SECURITY.md) §Key management）。
- 部署用 `pm2 start scripts/ecosystem.config.cjs --only X` 让 env 块注入；裸 `pm2 start server.js` 会丢 env（已在 `CLAUDE.md §部署雷区` 标注）。

### G5 · 防滥用怎么做的？

- nginx `limit_req_zone $binary_remote_addr zone=attrax_api:10m rate=10r/s`，`/api/scan*` burst=20，`/` burst=40。
- BFF `lib/rate-limit.ts:checkRateLimit('scan:${clientId}', 10, 60_000)`，按 `X-Real-IP` 哈希，单进程固定窗口。
- RAG `_RATE_LIMIT_MAX_REQUESTS=30` / 60s 进程内 deque，写入端点二次限流。
- fail2ban：`sshd` / `nginx-auth` / `nginx-botsearch` / `recidive` 4 个 jail。

### G6 · 上传的文件会被病毒扫描吗？

当前没有接 ClamAV。但上传链路做了强校验：MIME + 扩展名 + magic bytes + 大小上限（DOCX 还校验 ZIP 结构）。攻击者构造合法图片 / DOCX 不会绕过限流，但理论上能消耗扫描配额。

## H · 工程亮点（适合技术评审）

### H1 · 最值得讲的工程决策

**de-RAG 改造（2026-09-11~17）**：

- 旧方案：LangGraph 状态机 + FAISS 向量库 + PAI embedding + 自建 NLI 验证。
- 新方案：「KB 锚点 + 法规原文 + LLM 按锚点生成 + 确定性字面匹配」，线性 3 步。
- 收益：embedding 栈整组去掉（不再依赖 ModelScope / PAI / Ollama）；生成时间稳定；引用真实性可机器校验。
- 落地路径：先塌缩 LangGraph 为线性 3 步（保留所有 `agent_trace` 不变式），再删除 embedding，最后引入 quote_matcher 替代 NLI verifier。

完整 spec：[`docs/plans/2026-09-11-de-rag-evidence-spec.md`](docs/plans/2026-09-11-de-rag-evidence-spec.md)。

### H2 · 自失效缓存

`rag_service/retrieval/{kb,article}_loader.py` 用 `(mtime_ns, size)` stamp 检测磁盘变化。watchdog 03:00 自动改 YAML 后，长跑 RAG 进程**下次 verify 自动清缓存、按新法条重比对**，无需重启。`verifier.py:_sync_article_cache` 用 generation tick 协调下游缓存。**读路径永远不主动调 `invalidate_cache()`**——文档明确警告这会让 5 分钟一次的 `/ready` 探针触发每次全量重解析，约 288 次 / 天无效重解析。

### H3 · 双供应商降级

视觉与报告生成都做 MiniMax + DeepSeek 双供应商，关键踩坑全部写在代码注释里（DeepSeek reasoning 预算、Anthropic 兼容端点响应块顺序、重试预算会吃掉降级机会）。

### H4 · fail-closed secret

`RAG_INTERNAL_SECRET` 在 `main.py:_enforce_secret_policy` 做强制策略：

- prod 空 secret → `RuntimeError` 拒启动
- 非 prod 空 secret → 自动生成 ephemeral secret（仅本进程有效）
- `RAG_ALLOW_INSECURE=true` → 显式 opt-out（打 WARNING）

这套机制防止「运维忘了设 secret → `/scan` 写端点完全开放 → 任何能连到 8001 的人都能烧 LLM 配额」这种灾难。

### H5 · BFF 双层限流

nginx 10 r/s + BFF 10 / 60s（差 60 倍）。BFF 才是真实成本控制，因为 nginx 单锁释放后还要走 worker 限流 30 / 60s；BFF 是 60 秒 10 次窗口，超过就 429，不会让请求打穿到 LLM。`lib/rate-limit.ts` 注释里写明：「一旦扩到多实例，必须重新引入跨进程锁」。

### H6 · Next 16 standalone 部署

Next 16 + Turbopack 不再自动复制 `.next/static/` 到 `standalone/`，`public/` 也不复制。我们用本地 `build-deploy-tarball.sh` 在 stage 阶段把 `.next/static/` + `public/` 一起打进 `standalone/`，服务器 nginx alias 直出。详见 [07-deployment-and-operations.md §Next 16 雷区](./07-deployment-and-operations.md) + [`docs/infra/NEXTJS-16-STANDALONE-NOTES.md`](docs/infra/NEXTJS-16-STANDALONE-NOTES.md)。

## J · 可能被挑刺的问题

### J1 · 引用失败的 citation 怎么办？

`match_status == "unmatched"` 的会被前端标红。结果页 EvidenceRequestPanel 提示用户「点击补充证据」（J10 流程：上传更多图 / 文档 → `POST /api/v1/scans/{id}/evidence` → `POST /api/v1/scans/{id}/revisions` 触发重扫）。完整 J10 实现见 [`lib/result/inspection-view-model.ts`](lib/result/inspection-view-model.ts) 与 [`rag_service/application/scans.py`](rag_service/application/scans.py)。

### J2 · 跨境电商本身的合规要求（欧代 / 海关）你们覆盖吗？

部分覆盖。`EU-2019-1020-market-surveillance` 监管条例（含欧代 / 海关抽查）已加入 watchdog 监控源。完整覆盖还需要对接海关数据 + 平台卖家政策（如亚马逊 EPR），这是后续路线图。

### J3 · 怎么证明你的报告真的「权威」？

三道关：

1. **来源关**：所有法规都是 EUR-Lex / eCFR / 国务院公报 / CPSC 官方一手源。
2. **验证关**：每条引用确定性字面匹配，引用真实性可机器校验（`auditMetadata.verificationMode = "kb_exact_quote"`）。
3. **时效关**：35 个官方源每日自动巡检 + 自动入库，无人为遗忘。

但需要承认**：attrax 是初筛工具，**不替代法务**。结果页底部明确写「本报告仅供参考，不构成法律意见」。

### J4 · 别人复制你们的方案难吗？

中等。技术栈本身不复杂（Next.js + FastAPI + LLM 任何人都能搭），真正的护城河是：

1. **44 篇法规 + 44 个 KB 锚点的精修**：每个 anchor 的 `key_points` / `risk_hint` / `key_articles` 都是人工精修过的，是持续投入的运营资产。
2. **35 个 watchdog 监控源 + 自动入库四类语义**：运营系统不是一次性开发能搭出来的。
3. **确定性引用验证 + 三态前端反馈**：闭环 UX 也是长期打磨。

### J5 · 用了 OpenAI / Anthropic 之外的国产模型，理由？

成本 + 合规。MiniMax-M3 是国内 Anthropic 兼容端点，单价比 OpenAI 低、调用链在中国境内（数据出境风险低）。DeepSeek 是 reasoning 模型，作为 MiniMax 不可用时的兜底。

### J6 · 你们怎么不上 ChatGPT / Claude？

我们实际用过 MiniMax-M3（Anthropic 兼容）做主力 — 它在中文合规场景的中文表达 + 多语言引用上比 GPT 系列稳。OpenAI / Anthropic 的 GPT-4 / Claude 作为备份候选，但数据出境成本高，且本场景 LLM 替换很轻量（换 base_url + model 名即可）。

### J7 · 数据喂给模型会不会让竞品学到？

不会。我们喂给模型的：

- 法规原文（公开数据，无商业价值）。
- 视觉识别结果（用户上传图，仅用于当次扫描）。
- KB 锚点（精修过的人工知识）。

这些都不构成可学习的「业务秘密」。
