## 二、目标

### 2.1 用户场景

```
用户上传产品图片 + 选择目标市场
    ↓
attrax 识别产品类别
    ↓
从法规语料库检索相关条款
    ↓
生成含原文引用的合规报告
    ↓
用户导出 / 分享报告（PDF/Markdown）
```

### 2.3 核心要求

| 要求 | 说明 |
|------|------|
| **可溯源** | 每条结论必须注明法规名 + Article/条款 + 页码 |
| **引用原文** | 报告中包含被引用法规的实际文本（blockquote） |
| **精准** | 不夸大风险，不遗漏条款，不编造条款 |
| **可导出** | Markdown / PDF 格式，可直接给客户/海关 |
| **可迭代** | 法规更新时可增量更新语料库 |

## 三、架构方案

### 3.1 整体架构

```
用户上传产品图片
       │
       ▼
┌─────────────────────────────────────────────────────┐
│  Vision 识别 (Claude/GPT-4V)                      │
│  → 产品类别 + 市场 + 关键参数                      │
└────────────────────┬──────────────────────────────┘
                     │
                     ▼
┌─────────────────────────────────────────────────────┐
│  查询分解 (Query Decomposer)                        │
│  → 生成检索 query + market filter + keywords        │
└────────────────────┬──────────────────────────────┘
                     │
                     ▼
┌─────────────────────────────────────────────────────┐
│  混合检索 (Hybrid Retrieval)                        │
│                                                     │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────┐ │
│  │ Dense检索    │  │ BM25检索     │  │ 元数据   │ │
│  │ (向量相似度) │  │ (关键词)     │  │ 过滤     │ │
│  │  Top-50     │  │  Top-50     │  │ market   │ │
│  └──────┬──────┘  └──────┬──────┘  └──────────┘ │
│         └─────────────────┼──────────────────┘       │
│                           ▼                        │
│         RRF 融合 (Reciprocal Rank Fusion)             │
│                           ▼                        │
│         Cross-Encoder Rerank (BGE-reranker)         │
│                           ▼                        │
│                  Top-10 Chunks                      │
└────────────────────┬────────────────────────────────┘
                     │
                     ▼
┌─────────────────────────────────────────────────────┐
│  LLM 生成报告 (Claude 4 Sonnet)                    │
│                                                     │
│  Prompt 要求:                                       │
│  - 逐条注明: [法规名, Article, 页码]               │
│  - 引用原文: 用引用块标记原文                       │
│  - 区分"已核实"和"推断"                            │
│  - 超出范围时说明"未在语料库中找到依据"            │
└────────────────────┬────────────────────────────────┘
                     │
                     ▼
┌─────────────────────────────────────────────────────┐
│  报告输出                                          │
│  - 带引用的 Markdown / PDF                          │
│  - 每条结论附法规溯源                               │
└─────────────────────────────────────────────────────┘
```

### 3.2 语料库构建流程

```
原始文档 (PDF/DOCX/HTML)
       │
       ▼
┌─────────────────────────────────────────────────────┐
│  解析层 (Parser)                                    │
│                                                     │
│  PDF ──► pdfplumber ──► 文本 + 表格 + 页码          │
│  DOCX ──► python-docx ──► 段落 + 表格              │
│  HTML ──► BeautifulSoup ──► 正文 + 表格            │
└────────────────────┬────────────────────────────────┘
                     │
                     ▼
┌─────────────────────────────────────────────────────┐
│  分块层 (LegalChunker)                              │
│                                                     │
│  策略: 按法规条款分割，不按固定 token              │
│                                                     │
│  EU法规: 按 "第X条" / "Article X" 分割             │
│  DOCX: 按段落 + 表格分割                            │
│  HTML: 按标题 + 正文分段                             │
│                                                     │
│  每个 chunk 包含:                                   │
│    - content: 文本内容                             │
│    - doc_name: 法规名称                             │
│    - source: 条款编号（Article / 第X条）            │
│    - page: 原文页码                                 │
│    - market: 适用市场                                │
│    - keywords: 关键词标签                            │
└────────────────────┬────────────────────────────────┘
                     │
                     ▼
┌─────────────────────────────────────────────────────┐
│  向量化层 (Embedding)                                │
│                                                     │
│  模型: voyage-multilingual-3                        │
│        (支持中日韩英混合嵌入，体积小、速度快)        │
│                                                     │
│  每个 chunk → 768维向量 → 存入 Qdrant               │
└────────────────────┬────────────────────────────────┘
                     │
                     ▼
┌─────────────────────────────────────────────────────┐
│  语料库存储 (data/corpus/)                          │
│                                                     │
│  data/corpus/                                       │
│  ├── eu/               ← EU 法规预解析 JSON         │
│  ├── us/               ← 美国法规预解析 JSON        │
│  ├── asia/             ← 亚洲法规预解析 JSON        │
│  ├── products/         ← 产品专项分析 DOCX 解析     │
│  └── index.json        ← 全量索引（快速检索用）     │
│                                                     │
│  (向量数据存 Qdrant，JSON 只存 metadata)           │
└─────────────────────────────────────────────────────┘
```

### 3.3 分块策略（核心）

```
❌ 错误做法（固定 token 切分）:
   "第17条第一款：制造商必须在产品上标注CE标识。..."
   "第二款：制造商应随产品提供使用说明书..."

   → 被切成两块，检索时只得到半句话

✅ 正确做法（LegalChunker）:

   Step 1: 找所有条款边界
     "第17条" → [0, 200]
     "第18条" → [200, 450]
     "Article 22" → [450, 700]
     ...

   Step 2: 以条款为单位成块
     Chunk 1: "第17条 [全文]"
     Chunk 2: "第18条 [全文]"
     Chunk 3: "Article 22 [全文]"
     ...

   Step 3: 太短的块（<200 tokens）合并到下一个

   Step 4: 表格单独成块
     Table Chunk: [表头 + 前3行数据]
```

### 3.4 检索流程（精确）

```
输入 query: "锂电池充电宝，出口欧盟和美国"

Step 1: Query 分解
  market = ["EU", "US"]
  keywords = ["锂电池", "充电宝", "便携式储能", "lithium", "power bank"]
  products = ["电子产品", "电池供电"]

Step 2: 并行混合检索
  Dense检索:
    - 向量模型: voyage-multilingual-3
    - Top-50 结果

  BM25检索:
    - 全文关键词检索
    - Top-50 结果

  元数据过滤:
    - market IN [EU, US]

Step 3: RRF 融合
  score(chunks[i]) = 1/(60 + rank_dense[i]) + 1/(60 + rank_bm25[i])
  取 Top-20

Step 4: Cross-Encoder Rerank
  - 模型: BGE-reranker-v2-m3
  - 对 Top-20 重排
  - 取 Top-10

Step 5: 组装上下文
  Chunk 1: [REACH Article 22, p.156]
  Chunk 2: [EU《新电池法》Article 61, p.89]
  Chunk 3: [FCC 47 CFR 312, p.3]
  ... (带完整原文引用)
```

## 四、技术选型

### 4.1 组件选型

| 环节 | 选型 | 版本 | 理由 |
|------|------|------|------|
| 向量库 | **Qdrant** | Docker latest | Rust 实现性能高，支持 metadata filter，Docker 一键启动 |
| 嵌入模型 | **voyage-multilingual-3** | latest | 支持100+语言，中日韩英混合嵌入效果最佳 |
| Reranker | **BGE-reranker-v2-m3** | latest | 中文法规 rerank 效果最佳，开源可本地部署 |
| Orchestration | **LlamaIndex** | 0.10.x | 企业 RAG 事实标准，组件可插拔，Python |
| PDF 解析 | **pdfplumber** | latest | 已验证 100% 成功，Windows 兼容，表格支持好 |
| DOCX 解析 | **python-docx** | latest | 直接读取 XML，无需外部依赖 |
| HTML 解析 | **BeautifulSoup4** | latest | 容错性好，配合 lxml 加速 |
| LLM | **Claude 4 Sonnet** | latest | 已有 SDK，中文生成质量高，工具调用强 |
| 分块策略 | **自定义 LegalChunker** | 自研 | 按条款边界分割，非固定 token |

### 4.2 基础设施要求

| 组件 | 资源 | 说明 |
|------|------|------|
| Qdrant | 2核4G | Docker 起一个实例，本地运行 |
| Embedding 模型 | GPU 推荐 | 可用 CPU（较慢），voyage API 可云端调用 |
| Reranker 模型 | GPU 推荐 | 可用 CPU，BGE 可本地部署 |
| Python 运行时 | 任意 | 用于语料库构建脚本 |

### 4.3 依赖安装


## 六、实施计划

### Phase 1：语料库构建（1-2天）

```
目标: 将现有 60+ 法规文档解析并入 Qdrant 向量库

步骤:
1. 安装 Python 依赖
2. 运行 build_corpus.py 解析所有 PDF/DOCX
3. 运行 ingest_to_qdrant.py 入 Qdrant
4. 验证: 用 test_retrieval.py 测试 query

优先级排序:
  1. EU 法规 PDF（18个，质量最高）
  2. 合规产品 DOCX（9个，含量化数据）
  3. HTML 法规（选 10 个质量较好的先处理）
  4. 截图 PDF（7个，暂时跳过）
```

### Phase 2：检索验证（1天）

```
目标: 手动测试检索精准度

步骤:
1. 准备 10+ 个测试 query（按产品+市场组合）
2. 检查 Top-10 是否召回正确条款
3. 调整 chunk size / reranker threshold
4. 确认召回率达标（目标: 90%+ 准确）

测试 query 示例:
  - "充电宝出口欧盟要哪些认证"
  - "乒乓球拍进入欧洲需要满足什么法规"
  - "锂电池产品美国FCC认证要求"
  - "带蓝牙功能产品出口欧盟"
```

### Phase 3：接入 attrax（2-3天）

```
目标: 将检索管线接入现有 API Route

步骤:
1. 将检索管线封装为 Python HTTP 服务（或用 Next.js API Route）
2. 修改 app/api/scan/route.ts 接入文档检索
3. 接入 Claude LLM 生成报告
4. 前端展示报告（引用溯源高亮）

关键: 报告每条结论必须带 [法规名, Article, 页码] 引用
```

### Phase 4：报告导出（1天）

```
目标: 支持导出 Markdown / PDF

步骤:
1. 报告页面添加"导出"按钮
2. Markdown 格式直接导出
3. PDF 格式用 puppeteer 或 markdown-to-pdf
4. 每条风险点附原文引用（blockquote）
```

```
       ▼

       │
       ▼
验证检索效果
```

## 八、风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| HTML 解析质量差 | 召回率低 | 优先处理 HTML 中内容质量好的；质量差的用 OCR 转 PDF 再处理 |
| REACH 849页分块过多 | 检索噪音大 | 按市场/产品关键词预过滤，减少无关召回 |
| LLM 幻觉 | 报告引用不准确 | Prompt 严格约束，必须引用原文；超出范围的条款必须说明"未找到" |
| 法规版本更新 | 旧条款过时 | index.json 带版本号和发布日期；query 时显示版本信息 |
| 截图类 PDF 无法解析 | 7个文件无法使用 | 评估后若关键法规则人工转文本；否则暂时忽略 |
